# 自有技能与全局 AGENTS.md 审计

日期：2026-09-07。源码基线：`44476a0`。

审计对象为 `skill-foundry/skills` 的 11 个自有技能及 `~/.codex/AGENTS.md`。其中 10 个技能有全局安装副本；`awesome-presentation` 仅在本仓库发现，单独标记为未安装。按用户修正后的范围，外部安装技能、第三方插件、所有 `lark-*` 均不纳入结论。

本轮交付静态审计及具体修改建议，没有修改技能、安装副本或全局规则。静态发现不等于已证明模型在真实任务中发生误触发；本轮未进行完整行为验收。

## 文章依据与判断标准

已阅读 Eric Provencher 的 [Rethinking skills and prompts for GPT-6 Astra](https://x.com/pvncher/status/2095991462416490862) 英文正文和两张示例图。X 页面直接访问返回 403；通过 [FxTwitter 对应帖子的文章内容](https://api.fxtwitter.com/pvncher/status/2095991462416490862) 取得正文，并用 X 的 syndication 响应核对作者、标题及文章 ID `2095989703967125509`。

文章主张：描述简短且能准确选择技能；复杂入口按需路由；详细步骤服务于真实约束；全局指令只保留跨任务需要的内容；授权边界和完成标准应避免任务过早停止。这些是本轮的审计维度，不是删除用户明确偏好或安全要求的理由。

## 核心判断

全局文件共 67 行、2,131 字符，不存在每次修改必须通读仓库的规定，无需整体推倒。更主要的负担来自技能内部的额外批准关卡、重复入口和把多种工作模式压进同一条固定流程。

最值得优先处理的是 `browser-harness`、`awesome-presentation`、`trigger-build-workflow` 的决策边界；其次是 `asset-validation` 的模式路由和 `tdd` 的重复发现。保留数据库迁移保护、公网发布授权、凭证保护、精确进程清理及任务内提交要求。

## 已确认的问题

### A1：浏览器验收完成后仍有无条件批准关卡

证据：[browser-harness/SKILL.md](../skills/browser-harness/SKILL.md) 第 30–33、137–157 行。

普通前端改动已验收通过时，技能仍要求在 cleanup 前询问是否远程走查，并等待回答、保留 dev server。这给每次前端任务额外加入一个与交付无必然关系的停顿，也延后资源清理。该要求来自技能，不能归因于用户当前要求。

建议改为：验收通过后默认清理本任务资源；已有明确远程走查或保留服务要求时，执行对应分支并报告 URL、进程和保留原因。创建公网隧道仍须有用户授权，已经授权的请求不重复询问。

### A2：演示技能明确拒绝接受用户的内容授权

证据：[awesome-presentation/SKILL.md](../skills/awesome-presentation/SKILL.md) 第 35–41、62–65、78–93 行；[content-discovery.md](../skills/awesome-presentation/references/content-discovery.md) 第 17–30 行；`agents/openai.yaml` 的默认提示。

用户说“直接做／别问了／你定”，或已经指定材料与目录，技能仍要求大纲批准、分段确认和独立目录确认。支撑文档还把“不批不做”明确写成无法跳过的条件。它会把已授权的完整交付降成等待批准的大纲。

建议保留两条路线：用户要求共同打磨内容时走讨论；材料和目标足够或用户授权自行决定时，整理内部页表后直接完成实现、构建和浏览器验收。只对影响正确性的材料缺口、非空目录合并、真实覆盖风险提问。入口、引用文档和默认提示必须一起调整，否则旧关卡仍会被重新加载。

本机未安装该技能，因此这是仓库资产问题，不能用它解释当前所有会话的停顿。

### A3：工作流兼容性被当作触发构建的决定条件

证据：[trigger-build-workflow/SKILL.md](../skills/trigger-build-workflow/SKILL.md) 第 3、16–24 行；[dispatch-build-workflow.ts](../skills/trigger-build-workflow/scripts/dispatch-build-workflow.ts) 第 259–281、347–350、355–372 行。

描述同时接受提交代码、打包产物和发布请求，但实际路线只按仓库是否有兼容 workflow 决定是否 dispatch。脚本始终包含 push；发现兼容 workflow 就要求 changelog 并准备运行工作流。这样，“提交并推送，但这次不构建”缺少表达渠道；“本地打包”也不应自动落入 push 路线。

建议先依据当前请求和已有授权确定操作：本地提交、提交并推送、触发构建、发布。兼容性检测只回答某条路线是否可执行。脚本需要能表达仅提交、仅推送和明确 dispatch；不可只靠修改 description 掩盖实现没有分支的事实。已有发布授权应直接执行，无需新增普遍确认关卡。

这是静态控制流发现；本轮未执行 push 或 workflow dispatch。

### A4：静态审查入口被完整验收规则包围

证据：[asset-validation/SKILL.md](../skills/asset-validation/SKILL.md) 第 8–25、37、41–58 行。

第 44 行提供 review-only 路线，但此前已经无条件要求真实 CLI/tmux、任务投喂和验收状态机。第 56 行又要求有人值守时先确认资产类型和目的，即使请求里已经写清。静态审查使用者需要自行解释哪些 HARD CONSTRAINTS 不适用。

建议把模式选择放到入口最前：静态审计只读资产和相关引用，按需做格式／语法检查；明确要求行为验收时才加载 CLI、隔离、观察、记录、重跑协议。类型和目的已明确时直接记录，缺失且影响执行时才问。真实验收中的独立评分、凭证脱敏、隔离和精确清理均保留。

### A5：tdd 在同一 Codex 会话重复发现

证据：本会话技能目录同时列出 `~/.agents/skills/tdd/SKILL.md` 和 `~/.codex/skills/tdd/SKILL.md`；两份入口与仓库源码 SHA-256 完全相同。

重复注册不会增加能力，却重复占据选择上下文并产生两个同名入口。建议每个宿主只保留一个被发现的安装入口，跨宿主安装可以保留；统一从仓库真源同步，避免日后两份内容漂移。本轮未删除安装副本。

`tdd` 第 3 行的全开发触发是 README 明确声明的现有设计，也与用户的全局开发要求有关，不能简单判成 bug。可以保留该策略并先缩短描述，避免重复列举 feature、scaffold、API、UI 和中英文关键词；是否收窄触发属于偏好调整。

### A6：仓库现有运行时检查与 SSH 技能不一致

实际运行 `bun scripts/check-runtime-contract.ts` 返回 1，报告两项：

- `persistent-ssh-ops/scripts/init-server-config.ts` 的 Git mode 是 `100644`，不满足检查器的 `100755` 要求。
- `persistent-ssh-ops/scripts/server-runtime.zsh` 被统一禁止 `.zsh` 的规则拒绝。

证据：[check-runtime-contract.ts](../scripts/check-runtime-contract.ts) 第 43–57 行；[persistent-ssh-ops/SKILL.md](../skills/persistent-ssh-ops/SKILL.md) 第 14–28 行。

SSH 技能明确需要安装 zsh runtime，文档又通过 `bun` 调用初始化脚本，因此这两条失败不能直接证明 SSH 功能失效。应明确区分“Agent 调用的 Bun 入口”和“安装到目标位置的 zsh 运行时资源”，同步修正检查器与 README 的运行时承诺；初始化入口的执行位按最终契约统一。不要为了让检查通过把必要的 zsh runtime 改写成不合适的实现。
