# 功能设计

设计文档只有一个目的：让用户用最少的阅读看懂改动并拍板，同时定下验收要逐项查什么。信息越多，困惑和来回沟通越多；能由 Agent 按技能和项目约定自行决定的，不进文档。

## 先调研

动手前查项目已有实现、依赖、相邻功能和可复用的组件或接口，项目知识走已有入口（如 repo-knowledge-graph）。调研过程不进文档，只留结论。同时从当前产品取真实的数据：名称、路径、ID、状态和已有文案，Demo 里直接用，不用占位数据，也不自造新文案。

## 什么要用户拍板

- 用户看到什么、怎么操作会改变；
- 数据或接口契约怎么变，尤其难以撤回的；
- 这次做什么、不做什么的范围取舍。

组件选型、token 取值、代码组织、测试方案按本技能和 `lobe-design` 自行决定，不拿给用户选。一项待拍板都没有时不出文档，直接说明，并按下方「验收清单」在回复里列出清单后开始实现。

## 版式：按场景，左右对比

- **顶部**：标题，加一段话说明数据从哪来、沿用了哪些现有能力或文案，并注明只是示意、不代表最终视觉稿。
- **待拍板**（有才写）：紧跟顶部，1～3 行，每行写问题、推荐和一句理由，不重复下面各列已经讲清的内容。
- **功能示意**（可选）：改动涉及规则、权限链路或状态流转时，在场景之前用一张流程或分层示意讲清机制，新增或改变的环节用改动色；没有机制要讲时不画。
- **主体**：按场景纵向排列，主路径在前，展开态、降级和边界场景在后。每个场景上方是编号标题和一两句场景描述，写清谁、在什么情况下、遇到什么；下方左右两列对比，左边「现状」，右边「改后」，各带一份仿真界面，界面下方用编号旁注逐条解释标注，需要时再加一条注释，交代不变的行为或边界。新功能没有现状时，左列放现有的相邻入口；真有两个可行方案时左右放 A/B。
- **标注**：在仿真界面上用虚线框直接圈出问题处和改动处，问题用红色，改动用绿色，框角的编号圆点与旁注一一对应，读者不读文字也能对上。
- **验收清单**：场景之后、页脚之前，写法见下方「验收清单」。
- **篇幅**：场景只列会改变用户所见的，通常 2～4 个；每个场景一屏内看完左右对比。页脚写文件位置，并注明不入仓库。

## 视觉语言

起草时复制 [设计文档模板](../assets/design-template.html)，保留样式和区块结构，换成本次的真实内容，不需要的区块整块删除。整份文档用同一套线框语言：纸面网格底、墨色细线框、衬线标题、等宽注记，强调色只用于编号和标注。

前端的仿真界面画成线框：保留产品真实的布局结构、信息层级、数据和文案，不还原产品的配色、组件外观和品牌。读者的注意力留在结构和行为上，也不会把示意当成定稿视觉。视觉还原本身是决策关键时，改在项目里起临时页面，用 browser-harness 截图嵌入。

默认静态。交互本身就是决策点，或要让人完整走一遍操作时，做成可点击原型：内联 JS 和模拟数据，各场景共用一份状态，在一处的改动在其他场景里同步体现；判定逻辑与真实实现或拟定方案一致，确认、校验、空态和操作反馈照实做，不连接真实服务。

后端同样按场景左右对比，画请求链路、状态流转或数据变化（内联 SVG 或 HTML 块），用真实的接口名、表名、字段和示例值，改动处同样圈出。

## 对外方案展示

功能已完成、要给客户或外部人员看方案但不能展示真实页面时，用同一视觉语言出展示页：去掉现状对比、待拍板和验收清单，改为功能示意、改后场景的可点击原型、规则与常见问题。文案和判定规则取自实际实现，组织、人员和价格换成示例数据并在顶部注明；不出现内部代码路径、服务与表名、租户或客户信息。

## 对比的取舍

「现状」本身就是对照。除此之外，真有两个可行方案时才并排放 A/B，并在待拍板里给出推荐；反例只在违反已有规则时出现，并标出规则编号。不为了对比造一个故意做坏的方案。

不写调研过程、被否决方案的完整论证、失败矩阵和实现步骤；确有必要时一句带过。

## 验收清单

验收查什么在设计环节定下，验收时逐项执行，不在验收时临场决定。有没有设计文档都要有这份清单。

- **来源**：每个场景的「改后」至少一项；再从 [交互与状态](frontend.md#交互与状态) 和后端失败路径里挑本次真会遇到的加载、空态、失败、无权限与恢复；本次改动可能波及的不变行为，按实际风险各列一项。
- **每项写法**：编号（`A1`、`A2`…）、操作与前置条件、可观察的预期、验证方式（浏览器 / 接口 / 测试 / 数据核对），所属场景由分组体现。预期用真实数据写成能判定对错的结果，如「筛选『已退款』无结果时显示空态和『清除筛选』，点击后恢复全部 24 条」，不写「体验良好」「正常显示」。一项只判一件事，不把多个结果捆成一项。
- **不进清单**：lint、类型检查、扫描和代码审查，它们属于实现阶段的确定性检查。
- **篇幅**：通常 4～10 项，一项一行，不展开论证。
- **在文档里**：用一张表，列为编号、操作与前置条件、预期、验证；按场景插入横跨整行的分组行，写场景编号、标题和项数，可能波及的不变行为单独成一组放在最后，失败与恢复路径在编号旁标「失败」。清单项每行写成 `<tr data-check-id="A1">`，分组行不带此标记，验收报告据此核对覆盖。窄屏时每项改为卡片，分组行保持整行。依赖待拍板项的预期写明跟随哪一项拍板，拍板后改成定稿结果。清单不单独请用户拍板，用户可增删改。
- **没有设计文档时**：开始实现前在回复里用几行列出同样的清单（编号、操作、预期），小修复通常 1～3 项。

## 形式与交付

- 单文件 HTML，CSS 内联，不依赖外部脚本、CDN、外部字体或构建（可点击原型的 JS 同样内联），`file://` 直接打开；放在 `<工作区根>/reports/<MMDD>-<主题>.html`。
- 交付前在浏览器打开一次，确认每个场景的左右两列在常用宽度下不挤，窄屏时改为上下排列，验收清单表在窄屏下不撑宽页面；可点击原型逐个走通主要操作，console 无报错。
- 交付时按 [分享链接](../SKILL.md#分享链接) 上传，回复里给公网链接。

用户拍板后直接进入实现，验收清单按拍板结果定稿。需求或决定有变时改同一份文档里的场景和清单，不另起需求文档或版本；验收前发现预期需要改变，先改清单并向用户说明，影响用户所见的变化先确认，不在验收时改写预期迁就实现。
