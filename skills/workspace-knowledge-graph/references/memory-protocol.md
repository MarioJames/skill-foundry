# 记忆协议

工作区记忆分两层文件,两层共用同一个写入条件:"这条信息对后续工作有没有价值":

- `.workspace/memory/daily/YYYY-MM-DD.md` 按天承载与某个日期、阶段、当前任务或短期接续相关的有价值信息,先提炼、全保留、不压缩。
- `MEMORY.md` 承载会持续影响工作空间或仓库后续行为的长期结论。

写入与消费规则由生成的 `AGENTS.md` 承载;`MEMORY.md` 和 daily 文件只放实际记录,无条目时 `MEMORY.md` 只保留标题与空占位。稳定项目事实仍应晋升图谱事实源(见"晋升与压缩");是否能从代码、git、PR、CI、任务系统或图谱事实源恢复不参与记忆写入判断,这些来源只在消费时用于事实核验和冲突处理。

## daily:短期价值层

### 写入时机

交付结论前完成记忆评估,但评估不等于必须写入:

1. 从本轮对话、决策和实施结果中提取候选信息。
2. 不直接复制事件摘要,先提炼为后续可复用的结论、约束、理由、线索或接续状态。
3. 只判断提炼后的信息对后续工作有没有价值;有价值才写,没有价值不为满足流程强行创建条目。
4. 价值判断通过后,与某个日期、阶段、当前任务或短期接续相关的信息写入 `.workspace/memory/daily/<今天>.md`;会持续影响后续行为的长期结论写入 `MEMORY.md`。

收尾评估不询问用户:毫无争议该记的内容直接记,有争议或可商榷的内容直接说明记了什么/没记什么及理由,不向用户确认“要不要记/记哪条”——那属于干扰。

### 用户通知

记忆发生变化时在最终答复中通知用户,只概括重点,不重复完整条目:

- daily 新增:`记忆已新增：<重点>`;daily 更新:`记忆已更新：<重点>`。
- `MEMORY.md` 新增:`工作空间全局记忆已新增：<重点>`;`MEMORY.md` 更新:`工作空间全局记忆已更新：<重点>`。
- daily 与 `MEMORY.md` 同时变化时分别通知;未产生记忆时继续明确说明`无该记内容`。

### 格式

```markdown
# 2026-07-23

- repo:imctl-ai — browser-harness 的插件内置与独立安装必须共用同一真源,后续修改需保持两侧一致。
- workspace — 记忆体系待把写入门槛收敛为后续工作价值,通知契约保持不变。
```

- 一天一个文件;文件不存在就新建,标题为 `# <日期>`。
- 每条单行，写成 `- repo:<repo>`（仓库名取 `.workspace/metadata.yaml` 的 `repo_order`）或 `- workspace`（跨仓或工作区级）。
- 行内写清动作和状态/下一步;多仓会话按对象分行。
- 先提炼、保持紧凑;写入后不压缩、不删除、不设保留窗口——旧文件即时间线索引,"上个月 xxx" 也应可查。

### 不记什么

- 对后续工作没有价值的信息,无论本轮是否修改了代码、文档或配置。
- 未经提炼的事件流水账,如仅说明完成了某次实现、版本调整、测试或例行图谱维护。
- 纯问答中没有产生后续可复用价值的内容。
- 凭证、token、账号、个人隐私、临时 ID。

## MEMORY.md:约束层

### 写入与层级选择

`MEMORY.md` 与 daily 使用相同的唯一写入条件:这条信息对后续工作有没有价值。价值判断通过后,只有会持续影响工作空间或仓库后续行为的长期结论才进入 `MEMORY.md`,如用户偏好、纠正、用户完成的外部操作、确认取舍和长期接续约束;与日期、阶段、当前任务或短期接续相关的信息留在 daily。

代码、git commit / PR、CI、任务系统、daily、当前外部状态或 `.workspace/` 事实源能否恢复该信息,不参与是否写入的判断。来源仍需如实归因:agent 推断只能标成推断,不能伪装成用户偏好或确认;凭证、敏感个人信息、临时 ID 和无关画像继续禁止写入。

### 条目类型

- `[偏好]`:用户明确表达、会在同一作用域后续复用的工作方式或输出偏好;已存在于用户级指令或 `AGENTS.md` 的规则不重复。
- `[纠正]`:用户纠正了旧名称、范围、归属、假设或目标。记录正确结论和被否定的误解,不能只写"已确认"。
- `[用户操作]`:用户在仓库之外完成的授权、部署、数据变更、发布、审批或环境操作。记录目标环境/对象和来源;再次依赖前仍验证当前状态。
- `[确认决策]`:用户明确确认、但无法从最终代码反推出理由的取舍。agent 自行判断不使用此标签。
- `[接续]`:未决问题、阻断原因、下一步和恢复条件。典型形态包括“方案已与用户对齐、待外部确认/审批/执行”:记录方案要点、待决事项和恢复条件(方案细节可引用 daily),执行完成或方案作废后删除。问题解决后删除,或在仍有历史价值时标明已被哪条结论替代;可引用 daily 现场(`背景见 .workspace/memory/daily/2026-07-22.md`)。

### Scope 分层

`MEMORY.md` 保持 Markdown,用机器稳定的标题表达父子作用域:

- `## workspace`:跨仓工作方式、工作区级称呼/纠正和影响多个项目的外部状态。
- `## repo:<repo>`:只影响 `repo_order` 中某个仓库的偏好、纠正或用户操作。
- `### task:<task-key>`:嵌套在 `workspace` 或某个 `repo:<repo>` 下,表示工作区级跨仓任务或该项目内任务。`task-key` 使用稳定的英文/数字 slug;任务完成且没有剩余语境时删除该小节。

相同 scope 的记录放在同一分节,不重复创建同名标题。稳定跨仓规则应晋升到图谱,只有无法被图谱表达的用户语境留在 workspace scope。

这里不改用 JSONL:它会为每条重复 scope/字段并增加转义噪声;也不使用 YAML,因为技能当前坚持零依赖解析,缩进错误会让整份记忆失效。scope 化 Markdown 仍能用 `rg '^## repo:...'` 精确定位,也便于人直接审阅。若未来出现大量自动查询/并发写入需求,再把结构化文件设为真源并生成 `MEMORY.md`,不要同时手工维护两份。

### 紧凑格式

```markdown
## repo:example-repo

### task:rename-entry

- `2026-07-10` `[纠正]` 来源:用户明确纠正;结论:后续统一使用 `new-name`,旧称不再作为入口。
```

每条记录保持单行,便于 diff、搜索和机械校验。日期表示获知或最后确认时间,不代表内容永远有效。同一 scope 下按日期由新到旧排列;新记录纠正旧记录时直接压缩或删除旧记录,不把 MEMORY 当不可变事件日志。

每条至少回答:范围(由 scope 父级表达)、来源(用户明确说明/用户确认/agent 观察/agent 推断)、当前有效结论(未来 agent 应据此改变什么行为)。若信息容易失效,补充"截至日期""待验证"或替代关系。当前用户指令纠正旧记忆时,直接更新、压缩或删除旧条目,不要留下两个看似同时有效的结论。

### 明确排除

- `bootstrap`、`scan`、`init`、`validate` 成功,扫描仓库数量和生成文件清单。
- 修改了哪些文件、实现了哪些函数、跑过哪些测试、精确产物数量、subagent / reviewer 流水账。
- 只罗列当前代码结构、仓库定位、关系、稳定命令、接口/字段或包清单,却没有提炼出后续工作价值的内容。
- 没有提炼出后续工作价值的完成摘要、文件清单、测试结果和流水账;不能只因事件发生过就写入。
- 密钥、token、账号、个人隐私、临时 ID、易变 URL/主机名或与工作无关的个人偏好。

## 消费门禁

- **时间指称**("昨天/前天/上周/前几天/那次"等):先换算为具体日期,打开 `.workspace/memory/daily/<date>.md`(无文件则看相邻日期),按行内对象标签定位;需要语境时跳 `MEMORY.md` 对应 scope,代码细节用 git 兜底。
- **续接语义**("上次/继续/之前/还是按原来")、恢复偏好/纠正/确认取舍/用户操作、对象称呼歧义:按 scope 和任务关键词定位 `MEMORY.md` 对应小节。
- 不默认读取整个 `MEMORY.md` 或整个 `.workspace/memory/daily/` 目录;daily 按日期文件直接打开,天然不超载。
- 权威顺序:当前用户指令 > 当前代码/配置/外部实时状态 > 图谱事实源 > 历史记忆。记忆只提供线索,不证明当前代码或外部状态,也不授权重复执行过去的部署、发布、迁移或数据操作。

## 晋升与压缩

- daily → `MEMORY.md`:短期信息后来被确认会持续影响后续工作时,提炼为对应 scope 的长期结论。
- 稳定对象称呼和任务触发词 → `.workspace/metadata.yaml` 的 `task_routes`。
- 仓库入口、非显然操作和误操作护栏 → 仓库 `index.md`。
- 业务边界、流程和共享机制 → `domains/` / `shared/`。
- 跨仓机制、契约面和双侧证据 → `.workspace/metadata.yaml`,再运行 `init` + `validate`。
- `MEMORY.md` 是长期价值层,不是不可变审计日志:每次相关任务结束时删除已解决接续、已失效外部状态和不再对后续工作有价值的内容;合并同一主题的重复条目。daily 永不压缩;需要追溯代码变更时使用 git/PR,不靠记忆保存事件流水账。

## 与 harness auto-memory 的边界

- **auto-memory**(用户级,harness 管):跨工作区仍有效的用户画像、工作方式偏好、反馈。
- **工作区记忆**(`MEMORY.md` + `.workspace/memory/daily/`):只在本工作区有效的活动记录、repo/task 接续、工作区级纠正/确认。
- 判断标准:"这条信息换个工作区还有效吗?" 有效 → auto-memory;否则 → 工作区记忆。同一事实不双写。

## 存量审计

刷新已有工作区时,对 `MEMORY.md` 做一次压缩评审:

1. 删除对后续工作不再有价值的纯流水账;是否可由 git、代码、CI、任务系统、`.workspace/` 或 daily 反查不作为删除条件。
2. 把仍有价值的稳定事实晋升到正确事实源。
3. 将用户偏好、纠正、用户操作、确认决策和接续状态归入 `workspace` / `repo:<repo>`,任务语境再嵌套 `task:<task-key>`,改成带日期、类型、来源和结论的单行记录。
4. 删除已解决或已失效内容;无法确认是否仍有效时标为待验证,不把旧记录当现状。
5. Review Agent 对照本轮用户输入检查"该记而未记";脚本只能发现旧格式和明显流水账,不能推断缺失的用户语境。

## 为什么 daily 独立成文件

- 与日期、阶段和短期接续相关的信息若和长期结论混在一起,会迫使 `MEMORY.md` 滚动压缩。分文件后 daily 天然按时间分片,长期层只保留持续有价值的结论。
- 时间指称查询与文件组织同构:日期 → 文件名,O(1) 定位,不用扫描全部 scope。
- git diff 干净:每天一个新文件,而不是在同一文件同一区域反复改写。
- 置于 `.workspace/` 受管目录内:根目录裸 `memory/` 有被当作普通目录误删的风险,`.workspace/` 是工作区级持久状态的约定位置,生成器不管控 daily 内容,只幂等建目录。
