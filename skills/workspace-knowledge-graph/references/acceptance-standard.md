# 验收标准

在 Writer Agent 写入事实源并运行 `init` 之后使用。

1. 先跑脚本校验。`validate` 证明结构、链接和 registry 机制正确。有报错就修事实或生成产物并重跑 `init` + `validate`；不要开始语义评审。
2. 脚本校验通过后，派 Review Agent 做只读语义评审。Review Agent 不编辑文件，只比较 Research 证据包、`.workspace/state/discovery.json`、Writer 沉淀的事实源和生成文档。
3. Review Agent 的发现不是脚本硬失败；按下方裁决形态归并。`must_fix` 交回 Writer Agent 修补，然后重跑 `init` + `validate` 并复查受影响部分。

这个只读阶段不能替代 [research-protocol.md](research-protocol.md) 的 Research/Writer 扇出闭环。

## 裁决形态

把每条发现归为：

- `must_fix`：阻碍图谱成为可靠的工作区入口
- `should_fix`：有价值的缺口，等证据齐了应该修
- `acceptable`：已评审并有意保持现状
- `needs_human_judgment`：需要仓库证据之外的产品/团队知识

除非语义检查暴露了文件损坏、链接失效、解析错误、必需产物缺失或生成产物过期，否则不要把语义检查当成脚本硬失败。"还没读"不是 `needs_human_judgment`；去读仓库证据。

## 渐进维护

就绪门槛见 [progressive-maintenance.md](progressive-maintenance.md)（可用路由地图 + 有证据入口 + 重要业务域首版覆盖，不求穷尽）。评审据此定级：与任务无关的语义深度缺口最多标 `should_fix`。

评审问题：图谱是否给了未来 agent 一条清晰的规则——真实工作发现事实时如何充实图谱？Review Agent 还要确认 Research Agent 已经识别的重要业务域没有在 Writer 沉淀时被压成低密度总述。

## 记忆边界

警示信号：

- `MEMORY.md` 包含路由规则、仓库命令清单、稳定构建/测试事实、改动文件/产物数量、图谱策略或 commit 摘要。
- `MEMORY.md` 复制记忆协议、写入格式或消费门禁；这些规则应只存在于 `AGENTS.md`，记忆文件只放条目或空占位。
- 用户明确给出了工作偏好、纠正、已完成的仓库外操作、确认取舍或接续条件，后续仍会受影响，但 `MEMORY.md` 没有记录；缺失项无法靠脚本从最终代码推断。
- `MEMORY.md` 只堆积例行图谱刷新、`scan/init/validate`、生成产物和测试通过记录。
- 对象称呼或任务路由没有可打开证据、指向多处且无法消歧，或会误导后续任务进入错误仓库；这类 bad case 应标为 `must_fix` 或 `needs_human_judgment`，不要泛化成事实。
- 条目没有归入 `workspace` / `repo:<repo>` 父 scope，任务条目没有嵌套 `task:<task-key>`，或缺少 `[偏好|纠正|用户操作|确认决策|接续]` 类型、来源、当前有效结论；agent 推断被写成用户确认。
- 同一 scope/task 被重复创建，来源或结论为空，或条目用跨行正文堆积细节，导致检索和机械校验不稳定。
- 已解决、过期或互相冲突的内容仍像当前事实，没有删除、压缩或替代说明。
- `MEMORY.md` 复述了 `.workspace/metadata.yaml`、仓库 index、业务域/共享文档或 `discovery.json` 已有的事实。
- `AGENTS.md` 要求每次任务无条件读完整 `MEMORY.md`，或把记忆排在当前用户指令和当前事实证据之前。

期望动作：

- 只保留无法由代码、git/PR/CI、任务系统或图谱恢复，且会改变后续行为的条目；完整规则见 [memory-protocol.md](memory-protocol.md)。
- 对照本轮用户输入检查偏好、纠正、用户操作、确认取舍和接续是否漏记；不要从代码臆造用户语境。
- 把稳定命令、仓库操作事实、路由和图谱策略移到对应事实源；可由 commit/PR 恢复的实现摘要直接删除。
- 把稳定对象称呼和自然语言触发词移到 `task_routes.when`、仓库 index 或业务域/共享文档，确保用户下次直接提任务对象时能路由到项目和目录。
- 根入口只在续接、偏好/纠正/确认取舍/用户操作、未决状态或称呼歧义时按关键词读取相关记忆小节；当前用户指令和实时证据优先，历史记录不授权重复外部操作；再次依赖历史外部操作前先核验当前状态。

## 信息增益与删除候选

警示信号：

- 某段删掉后不影响任务路由、归属边界、入口选择、误操作防护或跨仓影响判断。
- 内容只是 manifest scripts、完整 API/方法/包/客户端/字段清单、扫描计数、版本、host 或目录树的散文化复述。
- 宽任务路由同时预加载仓库 index 和大部分 domain/shared，绕过 index 的二级路由职责。
- 默认 dev/build/test/install 或 npm/tnpm 等价命令被自动写入常用操作；类别字段夹带长摘要。
- `standalone_repos` 被理解为“简单仓库”或用于豁免本来复杂的业务域研究。

期望动作：

- 每段通过“行为增量”检查；不改变上述五类判断就删除。
- `AGENTS.md` 只给 first-hop。宽任务默认读取 1-2 个仓库 index，窄主题才直达单篇 domain/shared。
- 仓库 index 保留少量真实入口、非显然操作和高概率误操作护栏；领域文档保留边界、不变量、关键流程、维护影响与 1-3 个代表证据。
- 关系用“方向与机制 / 契约面 / 变更时检查什么”组织，双侧各取代表证据，不展开完整消费面。
- Review Agent 必须输出一轮删除候选；压缩冗余优先于补更多文档。

## 仓库操作事实

警示信号：

- 存在稳定操作来源（`package.json` scripts、`pom.xml`、shell 脚本、runbook、部署脚本、登录说明、测试说明），仓库 index 却没有有用的常用操作。
- 仓库 index 罗列了原始脚本名，却漏掉非显然语义，例如无 mock 开发模式、仓库专属旅程测试、shell 脚本才是真正的交付入口。
- 仓库 index 自动列出默认 dev/build/test/install、可由 manifest 一眼得到的 mock 脚本，或同一 script key 的多个 runner 拼写。
- Maven 服务被写得像前端包仓库，或暗示要用 `tnpm`。
- 操作行内嵌了易变值，却不指向声明它的文件。
- agent 撰写的正文携带会漂移的字面数量。

期望动作：

- 在 `.workspace/repos/<repo>/index.md` 补充精炼的操作事实并附证据链接。
- 优先提炼操作语义，而不是罗列原始命令清单。
- 把声明位置记为持久事实，把字面值当成带日期的示例。

## 资产孤岛澄清

警示信号：

- 某仓库或业务域孤立于关系图之外，路由名或摘要却暗示它属于核心链路。
- 独立仓库有大量页面/模块/package 或专属任务路由，却因 standalone 身份没有业务域入口。
- 资产仓库仅靠 README 证据或类别相似被关联。
- 扫描没有发现依赖证据，生成文档却没有解释这种孤立。
- 独立原因声称"其他仓库不依赖它"，证据却只指向孤立仓库自身，缺少对比的 manifest 或 `discovery.json`。
- 独立性结论只以「扫描无依赖证据」为据，而该仓库的技术栈本就不在自动检测覆盖内（检测只认 Maven 提及与生成客户端两类信号）。

期望动作：

- 真有集成时补上真实依赖证据。
- 否则在 `.workspace/metadata.yaml` 的 `standalone_repos` 记录边界。
- 不要把仅有类别相似编码成 `peer` 关系。

## 关系证据粒度

路径存在性已由 `validate` 覆盖。评审只看证据是否具体到能引导读者。

警示信号：

- 关系证据只有 `pom.xml`、根 `README.md` 或泛化集成目录之类的宽泛文件。
- 任务路由承诺链路调试、API 契约工作或跨服务诊断，关系证据却无法把 agent 引到具体的 facade、客户端、生成 service、路由、包或集成子路径。
- 关系只记了"仓库 A 调用仓库 B"，漏掉契约面（枚举见 [config-schema.md](config-schema.md) 的 relations）。

期望动作：

- 关系摘要保持仓库级，但包含连接机制和契约面。
- 路由承诺排障或契约工作时，补充代表性的具体证据。
- 关系事实留在 `.workspace/relations/registry.yaml`；仓库 index 链接相关仓库、关系类型和 registry 来源即可，不复制长摘要。

## 声明一致性

警示信号：

- 根定位声称某个集成，`standalone_repos` 或关系 registry 却否认它。
- 某条任务路由的 `when` 承诺了某能力，其证据所在的仓库却不在该路由的阅读列表里。
- 仓库 index 的职责/摘要断言了跨仓调用，registry 里却没有对应边，也没有独立边界说明。

期望动作：

- 把断言降到证据支持的范围，或补上缺失的有证据关系。
- 声明变更改 `.workspace/metadata.yaml`，然后重跑 `init`。

## 抑制透明度

警示信号：

- `.workspace/metadata.yaml` 含 `suppressed_relations`、`suppressed_relation_types` 或等价过滤。
- 生成的根文档和关系文档没有提到部分发现的关系被有意过滤。

期望动作：

- 补一条简短的生成说明，讲清抑制了什么、声明在哪里可查。

## 业务域覆盖均衡

零业务域核心仓库、缺 `## 摘要`、嵌套 `index.md` 等机械卫生已由 `validate` 捕获。评审只看语义质量。

警示信号：

- 文档罗列路径却不解释职责或流程。
- 摘要能解析但说不出有用信息。
- 相似仓库的业务域深度差异巨大且没有解释。
- 一个业务域被拆成许多小文档，制造不必要的跳转。
- 一篇过宽的文档掩盖了本应影响路由的多个独立能力。
- 核心仓库扫描到大量页面分组、Maven 模块、workspace 包或应用，却只有一篇笼统业务域文档，且该文档没有覆盖项目中重要领域事实。

期望动作：

- 保持 `domains/` 和 `shared/` 目录。
- 默认不拆分单个业务域。
- 只有文档大到影响阅读，或独立能力需要独立路由时才拆分。
- 对核心仓库，`domains/` 至少应覆盖任务路由承诺的主要能力；无法覆盖时把缺口标为 `should_fix`，如果入口因此无法可靠路由则标为 `must_fix`。

## 跨层冗余

警示信号：

- `AGENTS.md`、`MEMORY.md`、`.workspace/index.md`、仓库 index 和业务域文档重复同样的长摘要或路由解释。
- `AGENTS.md` 存放具体仓库细节，而不是持久的入口原则、路由、权威顺序和图谱维护规则。
- 根文档包含本属于仓库/业务域层的仓库内文件清单。
- `MEMORY.md` 包含路由、图谱策略、命令清单或任务路由内容，而非按 scope 组织的不可重建上下文。
- 仓库 index 罗列业务域/共享文档已归组、或 `discovery.json` 已有的大平铺清单。
- 仓库 index 复制完整关系摘要，而不是链接关系类型/方向到 `registry.yaml`。
- 两个仓库维护相关机制，共享文档之间却互不引用。

期望动作：

- 根文档聚焦阅读顺序、权威、任务路由和图谱维护原则。
- 把 `AGENTS.md` 当生成产物。持久的路由、关系和仓库顺序变更进 `.workspace/metadata.yaml`。
- 记忆按 workspace/repo/task scope 聚焦不可重建的用户语境、外部操作和接续状态。
- 仓库级事实和稳定操作留在仓库 index。
- 仓库内深度内容移到 `domains/` 或 `shared/`。
