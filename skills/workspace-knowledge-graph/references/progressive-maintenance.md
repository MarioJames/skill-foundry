# 渐进维护

这是让工作区知识图谱长期保持有用的运行契约。它有意把初始就绪门槛定在"可用的路由地图加有证据的入口"，把后续工作定为"小步、稳定、有证据的充实"。

## 渐进式图谱维护

初始化只需要创建可用入口：仓库边界、核心任务路由、关键关系证据，以及项目中重要业务域和共享机制的首版索引。不需要覆盖每个页面、接口、模块和历史工作流，但不能把多个会影响路由或维护判断的独立业务能力压成没有事实密度的概览。这类语义质量主要由 Research -> Writer -> Review 闭环保证，脚本只做兜底。

后续任务中，agent 通过 `rg`、读源码、调试、测试或集成工作发现稳定可复用事实时，应修补最小的正确事实源。`AGENTS.md` 只存每个工作区入口都必须消费的阅读顺序、路由、权威顺序和维护原则，不得存具体仓库细节。具体事实写入下列来源，然后由 `init` 刷新生成的入口文档。

- 仓库定位、入口和非显然命令：`.workspace/repos/<repo>/index.md`
- 业务域职责、关键流程和路径证据：`.workspace/repos/<repo>/domains/*.md`
- 跨切面机制、工具链、mock、测试、构建和协议层：`.workspace/repos/<repo>/shared/*.md`
- 跨仓依赖、契约面、双侧证据、独立边界和稳定任务路由：`.workspace/metadata.yaml`，然后重跑 `init`
- 无法由代码、git/PR/CI、任务系统或图谱恢复，且会改变后续行为的用户偏好、纠正、用户操作、确认取舍或接续状态：`MEMORY.md`，格式和消费门禁见 [memory-protocol.md](memory-protocol.md)

新增内容保持小步、有证据、与任务相关。不要为无关的全图重读打断当前任务；修补当前任务需要的事实，继续干活。

## 用户输入和对象称呼

真实用户经常直接说任务对象的自然称呼，例如功能名、项目代号、页面名、组件名、服务名、技能名或目录片段，而不是仓库名。第一次靠用户补充才定位成功时，必须把可复用的补全结果沉淀下来，避免下次再次询问同一信息。

- 用户原话里的对象称呼、简称、页面/组件/服务/技能/插件名：写进匹配的 `task_routes.when`、仓库 `index.md` 摘要/入口，或相关 `domains/` / `shared/` 文档。
- 该称呼对应的仓库、包、目录、主要入口和验证命令：写进 `.workspace/repos/<repo>/index.md`、`domains/` 或 `shared/`。
- 该称呼跨多个仓库或影响任务路由：写进 `.workspace/metadata.yaml` 的 `task_routes`，必要时补关系或独立边界。
- 无法由其他持久化工具恢复的用户偏好、用户纠正、用户完成的外部操作、用户确认取舍和接续状态：按 [memory-protocol.md](memory-protocol.md) 写进 `MEMORY.md`。agent 的临时判断只能标成推断，不能冒充用户确认。

不要把"刷新了知识图谱"、代码改动摘要或验证结果写入记忆。图谱、git/PR 和 CI 已记录这些内容；记忆只保留无法反推的用户语境、外部操作和接续状态。

坏例子要阻断或返回用户确认：称呼没有证据能落到具体仓库/目录；同一称呼稳定指向多个互斥入口且当前证据不能消歧；用户输入是一次性调试值、临时 ID、与工作无关的个人偏好或敏感凭证；沉淀后会让后续任务路由到错误项目。遇到这些情况，不要硬写路由或事实源，先标为 `needs_human_judgment` 或在评审中列为 `must_fix`。

## 信息密度门槛

图谱记录综合判断，不复制单次 `rg`、manifest、源码目录或 `discovery.json` 就能得到的清单。每段至少改变未来 agent 的一项行为：任务路由、归属边界、入口选择、误操作防护或跨仓影响判断；否则删除。

- `AGENTS.md`：条件化消费和 first-hop 路由。宽任务默认只指向 1-2 个仓库 index；窄主题才直达具体 domain/shared，不把某仓全部文档预加载进 route。
- `.workspace/index.md`：工作区定位、仓库矩阵和独立边界，不复述完整拓扑故事、接口或历史动作。
- 仓库 `index.md`：角色、边界、少量真实入口和非显然操作。默认 dev/build/test/install、manifest 脚本清单和同义 runner 不持久化。
- `domains/` / `shared/`：职责、不变量、关键流程、误操作风险、维护影响和 1-3 个代表入口；完整 API、方法、包、客户端和字段清单留源码或 discovery。
- 关系：方向和机制、契约面、双侧代表证据、契约变化时检查什么；不塞完整消费点/接口枚举。

Writer 完成后，Review Agent 额外做一轮“删除候选”评审：逐项指出可由权威来源直接恢复的重复内容、易漂移值和跨层复述，先压缩再考虑补充更多文档。

## 多仓联动

图谱应以工作区导航的密度保留重要的多仓联动。

真实工作暴露以下信息时，新增或完善跨仓事实：

- 方向：谁消费契约、谁提供契约。
- 机制：RPC、HTTP、OneAPI、代理、生成的客户端、路由、模块、共享制品等。
- 契约面：具体枚举见 [config-schema.md](config-schema.md) 的 relations。
- 双侧证据：消费方配置/调用点，加提供方路由/controller/模块/配置。
- 影响面：契约变化时应检查哪些仓库事实源、业务域/共享文档、测试或 mock 入口。

这一层保持精炼；粒度红线见 [config-schema.md](config-schema.md) 的 relations。

## 什么该加

图谱事实同时满足以下条件才加：

- 是做真实工作时发现的，不是靠目录名猜的。
- 足够稳定，未来 agent 会复用。
- 会改变路由、命令选择、归属边界、关系证据、跨仓契约理解或业务域理解。
- 能指向可打开的仓库路径、配置文件、脚本、controller、生成客户端、测试或 runbook。

用户第一次提供的稳定对象映射可以进入图谱，但要能由仓库证据验证；不可由仓库验证的用户偏好、纠正或外部操作走 [memory-protocol.md](memory-protocol.md)，不得为了满足路径证据要求而伪造证据。

不要加：

- 一次性调试观察、临时 ID、易变 URL、线上主机名、用完即弃的参数或个人便签
- 低密度清单：完整目录清单、完整接口表、字段级契约、错误码目录、mock 用例目录——除非当前任务明确需要该产物
- 精确计数——除非当前任务刚数过，且措辞写明是快照
- 行号锚点
- 读一下仓库就能回答的宽泛"可能"事实；去读证据

## 机械缺口 vs 语义缺口

`validate` 负责机械卫生：Markdown 表格畸形、嵌套反引号壳、链接/证据缺失、业务域/共享摘要非法、未决排查措辞、零命中的高信号代码标识符。

语义深度靠渐进维护。路由太宽、关系证据可以更具体、业务域文档可以更丰富——这些在阻碍或明显拖慢当前任务时再改。它们本身不构成"初始图谱不合法"的理由；但 Review Agent 发现核心业务域事实缺失到无法判断任务归属、入口或影响面时，应立即交回 Writer Agent 补进 `domains/`。

## 规则晋升

不要把项目特有的评审发现出现一次就变成技能策略。先修本地事实源。只有当一条规则跨工作区可复用、不需要项目知识就能机械检查或评审、且保护路由/证据/事实源完整性时，才晋升进本技能。

## 更新循环

1. 读当前任务指向的路由/文档路径。
2. 图谱缺少所需事实时，搜索或检查源码。
3. 修补最小的正确事实源。
4. 跑 `init`，让生成文档从事实源刷新。
5. 跑 `validate`，修掉本次修补引入的机械警告。
6. 继续原任务。
