# 反馈沉淀与归属

从用户指出的具体问题里找出下一次也应遵守的选择原则：是组件选错、重复封装、职责放错、偏离已有方案，还是遗漏基础行为；不要只记录原页面名和修补动作。

UI 工作中，遇到仅运行时暴露的缺陷、库行为与类型/文档/参数语义不符、同一规则用于三处及以上或跨页面重复修复、依赖/版本/Provider 约束踩坑时，将已验证且可复用的经验在同次修复中回流。记录现象、适用约束和验证方式，不写调试过程；没有运行证据时不将推测写成库约束。

| 经验归属 | 写入位置与读取入口 |
| --- | --- |
| Lobe 组件、token、视觉工艺、生态库及其依赖或 Provider 约束 | `lobe-design` 对应参考中的 `C-`/`D-`/`K-`/`E-` 编号规则，补充入口症状路由 |
| 通用交互、工程偏好与基础实现习惯 | 本技能对应参考，并更新 [规则索引](review.md)；项目已有 `ux` 负责的交互规则在 `ux` 维护 |
| 可确定检查的项目约束 | 项目已有 lint、类型检查或行为测试；无适合入口时再用本 CLI 的项目规则 |
| 单次产品决策、业务文案和状态流转定义 | 项目需求或业务测试，不写入通用技能 |

先查所属位置和已有调用入口，同一规则只在一处维护，其他技能引用其归属；不把组件库经验复制成另一份前端偏好，也不把自动门禁重复写成人工规则。

1. 对照原话与当前实现确认含义，检查同类组件、共享入口和相邻调用点，将能够预防同类返工的约束写成一句实话；明确表达的个人偏好不需要多项目重复出现才保留。
2. 按上表归档，判断它能否减少相似任务中的再次纠偏；有历史出处不等于值得收录。本技能保留工程选择、前后端习惯和项目范式，Lobe 组件与主题规则引用设计技能，不复制维护。
3. 能可靠判断的约束接入项目已有 lint、类型检查或行为测试；精确文本规则可用本 CLI 的 pattern，需 Agent 判断的偏好放入项目 review 规则，自动规则不在人工文档重复维护。
4. 项目规则先查重，同一原则补来源，互补细节保留，冲突遵循当前明确要求；用 learn 写入候选，核对实际命中、误报和作用域，再用 promote 激活，格式见 [脚本契约](rules.md)。
5. 技能参考补齐入口路由；已获项目规范沉淀授权时，在项目现有 Agent 入口加入简短读取指引，让下次实现前和交付前读取已落地的规则。已有入口则复用，原生 lint 接入已有检查命令，不另造配置层、不只把文件写下就算结束。
6. 下一轮用实际变动复验规则，检查是否提前拦住同类问题；误报时收窄范围或更换检测方式，修订先退回 candidate，过时规则设为 retired。

不要把单个页面的业务结果抽象成普遍规则，也不要把有依据的个人偏好删成泛泛的“遵循最佳实践”。来源和判断依据留在规则 sources，正文保持简洁；无需重建历史或调用 Jev。

本 CLI 默认落地到项目 .agents/feature-acceptance/rules.json，原生 lint 已能承载的规则只在原工具维护。需要复制 CLI 时复制完整 scripts/；本技能的 references 按需读取，扫描不再携带一份重复的通用审查索引。用户只要求审查时提供具体发现，不写项目规则或 Agent 入口。
