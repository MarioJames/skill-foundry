# 工程选择原则

- 先查项目已有依赖和实现，再选成熟库或成熟产品的已验证模式，不预设库里没有，也不无理由重写。
- 方案优先稳定和最小可用，当前需求用现有能力能完成时，不预建未来业务、兼容层和扩展体系。
- 非数据库变更默认直接采用最终方案，不为已经撤回的中间实现保留兼容分支。
- 同类功能优先沿用项目已有范式，参考现成实现的职责和调用关系，不只照搬目录名。
- 公共入口已经承担的配置、错误处理和状态管理，不在调用端重复包一层或维护另一份状态。
- 修改共享能力时检查同类入口和真实消费者，修复共同原因，不只补用户指出的一个页面。
- 简化实现保留已确认能力，局部需求不顺带扩成架构重写或产品改造。
- 包管理遵循项目指令、packageManager、锁文件和 CI，没有约定时按 bun、pnpm、npm 的顺序选择。
- 测试保护真实行为与失败路径，不为删除过的实现、新增文件数量或测试数量编写守卫用例。
- 方案里的假设先用现有代码和真实接口核实，不把供应商输出、默认值或上下游能力猜成事实。
