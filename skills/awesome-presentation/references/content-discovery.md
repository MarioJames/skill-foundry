# 内容发现：先聊清楚，再谈幻灯片

本阶段是技能的**主路径**。目标不是「尽快生成 slides」，而是和用户就**这场演示要说什么**达成共享理解。写法借鉴：

- **superpowers:brainstorming**：先设计后实现、**HARD-GATE**、一次一问、2–3 方案、分段确认
- **grilling**（mattpocock）：沿决策树逐枝追问、每题给推荐答案、事实自查 / 决策交用户、确认前不行动

## **HARD-GATE**

在用户**明确批准**「页级大纲 / Deck Spec」之前：

- **禁止** `tnpx … presentation init`、装依赖、写 `src/pages`、改 `registry`、跑 build/visual
- **禁止** 用版式、组件名或「我先 scaffold 一个项目」替代内容决策
- **禁止** 在同一条消息里连珠炮问 5 个问题后就开写
- **项目安装目录**属于实现闸门：可在 Spec 批准后的实现阶段再问，**不要**在内容发现阶段默认创建目录；也**不要**未问目录就 init

用户说「直接做 / 别问了 / 你定」时，仍至少交一版**完整页表 + 每页 takeaway + 建议砍掉的内容**，请其一句话确认；只有确认后才能进入实现。真正 trivial 的 deck（例如 3 页固定模板）可以把 Spec 压成几段话，但**不能不交、不能不批**。

### 「直接做」的响应合同

用户把内容取舍授权给你、又要求不要继续追问时，不再逐枝发问，但 HARD-GATE 不变。当前回复按以下顺序给出：

1. `Deck Spec` 元信息：听众、时长/页数、场景、核心主张、明确不讲、成功标准
2. 选定叙事弧及选择理由；必要时一句话说明放弃的备选
3. 完整页表：每页一行，至少含 `id / section / sectionEn / title / takeaway / intent 草案 / 证据或素材`
4. 裁剪记录：删除、合并、改口播、待补素材
5. 单独请求用户批准 Deck Spec

此时可以给每页一句内容提示，但**禁止用逐页上屏文案、口播稿或视觉稿代替页表**。缺少显式 `takeaway` 的页不算完成，未请求批准也不得进入实现。

## 原则

1. **一次只问一个问题**，等用户回答再往下。多题并行会让人懵。
2. **每题给出你的推荐答案**（grilling）：不要空泛开放题；写成「我建议 X，因为…；你也可以选 Y/Z」。
3. **事实自己查，决策交给用户**：已有讲稿、仓库文档、往期 PPT、目录里的材料——先读再问。听众是谁、砍哪页、主张是什么，必须用户拍板。
4. **沿决策树逐枝走**：先定「目的与听众」，再定「核心主张」，再定「叙事弧与页序」，再定「证据与禁区」，最后才是页表。不要在听众未定时纠结某一页文案。
5. **YAGNI**：演示不是百科。主动提议删页、合并、降级细节到附录/口播。
6. **多方案时给 2–3 条路径 + 推荐**：例如「故事型 vs 决策型 vs 教程型」叙事弧，说明 trade-off，默认推荐一条。

## 决策树（按序，可跳过已明确的枝）

不必机械走完所有叶子；但**未满足「就绪条件」就不得出 HARD-GATE**。

### 枝 1 — 目的与成功标准

- 这场演示结束时，听众应能复述/做到什么？
- 成功长什么样？（拍板、学会、对齐风险、要资源…）
- 失败模式是什么？（信息过载、没有行动、像读文档…）

### 枝 2 — 听众与场景

- 谁在场？角色、先验知识、决策权
- 场景：技术分享 / 课程培训 / 产品介绍 / 方案汇报 / 管理汇报 / 数据分析（可多选，但要定主场景）
- 时长与页数预算（例如 15 分钟 ≈ 8–12 页，不是 30 页）

### 枝 3 — 单一核心主张

- 整套 Deck **一句话主张**（不是主题词，是立场）
- 非主张是什么？（明确不讲什么）
- 若用户堆了多个主张：逼选主主张，其余降为支撑或拆成第二套 Deck

### 枝 4 — 叙事弧（2–3 方案）

给用户选项示例（按内容改写，不要照抄）：

| 方案 | 结构 | 适合 | 代价 |
| --- | --- | --- | --- |
| A 问题→方案 | 痛点 → 洞察 → 方案 → 证据 → 行动 | 方案/管理汇报 | 证据弱时易空 |
| B 教程推进 | 目标 → 步骤 → 示范 → 练习/注意 → 总结 | 培训/技术分享 | 易变长 |
| C 决策对照 | 背景 → 选项对比 → 推荐 → 风险 → 下一步 | 选型/立项 | 需要真实对照维度 |

推荐一条并说明原因；用户选定后再拆页。

### 枝 5 — 证据与素材

- 有哪些**可上屏**的事实：数据、截图、架构、命令、引用？
- 哪些只是口播、哪些必须可视化？
- 缺图/缺数时：标注「待补」或改用文字主张，**禁止**编造生产数据装真

### 枝 6 — 范围裁剪（grilling 重点）

对用户原文逐段施压：

- 这页删掉，主张还成立吗？
- 这是给听众的，还是给你自己的笔记？
- 三个要点能否压成一个 takeaway？
- 连续列表是否其实是一个流程/一个对比？

输出「建议保留 / 建议合并 / 建议删除 / 建议改口播」清单，请用户确认。

### 枝 7 — 页级大纲（Deck Spec）

只有前面枝基本清楚后，才写页表。格式：

```markdown
# Deck Spec: <标题>

## 元信息
- 听众：
- 时长/页数预算：
- 场景：
- 核心主张（一句话）：
- 明确不讲：
- 成功标准：

## 叙事弧
- 选定方案：A/B/C …
-  rational：…

## 页表
| # | id | section（中） | sectionEn（英） | title | takeaway（听众可复述） | intent 草案 | 证据/素材/右图 | 备注 |
| 1 | cover | 开场 | Open | … | … | cover | … | |
| … | | | | | | | | |

## 裁剪记录
- 砍掉：…
- 合并：…
- 待补素材：…

## 交付偏好（实现阶段再问，勿在此默认创建路径）
- 项目安装目录（**必问**，见 init-and-setup）
- 预览 / 单文件 HTML 等
```

**分段确认**：元信息 → 叙事弧 → 页表（可按章节分段）→ 裁剪记录。每段问「到这里对不对？」再往下，不要一股脑贴整篇等一个大 OK。  
**安装目录**：Spec 批准后再单独问；不要把「建在哪」埋进长 Spec 里默认替用户决定。

## 就绪条件（出 **HARD-GATE**）

同时满足才可进入实现：

1. 有一句**核心主张**与**成功标准**
2. **听众**清楚
3. **页表完整**：有序、每页一句 takeaway，页数与时长大致匹配
4. **裁剪**经过用户确认（或用户书面授权你代砍并接受结果）
5. 用户对 Deck Spec 有明确批准（「按这个做」「批准」「开干」等）

未满足时继续问/改 Spec，**不要** init。

## 问答风格示例

差：

> 主题是什么？听众是谁？要多少页？有没有数据？用深色主题吗？

好（一次一题 + 推荐）：

> 这场 20 分钟分享结束时，你更希望听众带走哪一种结果？  
> **我建议：A. 能讲清「为何要用 X 替换现状」并同意试点**（适合要资源/立项）。  
> 备选：B. 学会三个操作步骤；C. 仅对齐风险清单。  
> 你选哪个？或给更准确的一句话。

下一题等用户答完再发。

## 已有长文/旧 PPT 时

1. 先通读材料，提炼你认为的主张与页表草案  
2. **不要**从第一页开始逐字排版  
3. 用 grilling 挑战草案：「第 6–9 页都在重复收益，建议合成 1 页——可以吗？」  
4. 把用户纠偏写回 Spec，再批准

## 与实现阶段的边界

| 内容发现（本文件） | 实现（content-to-deck / init） |
| --- | --- |
| 主张、听众、弧、页表、takeaway、裁剪 | recipe、组件、registry、token、build |
| 决策与共享理解 | 工程与视觉门禁 |
| 产出：Deck Spec（对话内或落盘 md） | 产出：可运行项目 |

Deck Spec 可只在对话中维护；若用户希望落盘，写入项目内或工作区约定路径（例如 `<dir>/docs/deck-spec.md` 或用户指定路径），**仍须先批准再 init**。实现中若发现 Spec 与容量/证据冲突，停下来改 Spec 并再确认，而不是默默塞字或缩字号。
